# Reuse and upgrade checks

The [pilot](pilot-v1.md) preserves four implementations, including unsuccessful token outcomes. The repositories are public examples built by the maintainer's fully agentic Codex workflow: the maintainer selected scope, approvals and acceptance; agents implemented, tested and reviewed. The applications and fixtures remain on versioned branches; trial PRs stay unmerged.

## Machine readiness and project activation

Keep the normal installation scoped to the independently validated Matt/ECC update. Its owned installer pins upstream source commits, validates prerequisites and active identities, preserves unrelated configuration, and reports pending native sign-in/hook/resource/operational checks. Installation success alone is not operational acceptance. Native sign-in and changed hooks retain native review; never copy authentication, trust, sessions or caches between machines.

For experimental tools, the tested architecture separates machine readiness from project activation:

- Provision the immutable RTK executable and locked Graphify Python environment once per machine. Recreate the Python environment at a new absolute path rather than copying a virtual environment. Record versions, hashes and dependency closure.
- Activate RTK instructions and Graphify MCP only for an explicitly selected project/worktree. Keep RTK tracking/recall/configuration and graph state separate; each worker uses a server bound to its actual worktree, or explicitly selects the correct already-bound server. Rebuild after source, branch, HEAD or record changes. Registration and graph-file mtime do not establish freshness.
- An owned companion can run beside explicitly selected Matt project setup without editing, copying or patching upstream skills. RTK belongs in machine readiness plus project command policy; Graphify belongs in machine readiness plus exact-worktree MCP activation/indexing. Neither belongs in an unconditional global instruction to use it on every task.

The pilot does not authorize permanent integration. A future rollout would need a separately selected scope and new evidence; the normal installer does not activate these tools. The selected Graphify pin/path needs no paid account, API key, vendor activation or model backend for local code extraction/querying. Fresh-prefix proof is on Linux/Python 3.12, not every OS or unlimited hardware. Keep its ordinary resource bounds and licenses. See the [pinned source analysis and relocation proof](../protocol/graphify-local-v1.md) and [RTK fidelity/bypass policy](../protocol/rtk-v1.md).

## Existing Matt project setup

Do not assume rerunning upstream Matt setup is a safe generic updater. The setup-owned `project_check.py` companion in [the stack repository](https://github.com/loldlm1/.codex/pull/28) offers explicit `check` and `update` modes. Check writes nothing; current projects also receive zero writes from update. Recognized repairs preserve settled tracker, labels, vocabulary and custom instructions; conflicting or unsupported layouts return exact unresolved choices without partial planned changes. It does not silently select a new instruction surface, invoke first-time setup, or activate RTK/Graphify. Review its supported migration boundaries before using update.

## Proportional plugin upgrades

1. Select candidate Matt/ECC source commits deliberately. Save previous resolved identities, fingerprints and owned-file backups/restore manifest. Keep source pins and resolved active metadata consistent across native refresh; do not patch plugin caches.
2. Apply the owned installer in a disposable home. Exercise its existing external behavior tests: new/current/old/customized homes, preservation, backups, source identity and dependency repair. Validate native plugin metadata and prerequisites separately from actual operation.
3. Perform an actual hybrid task: Matt coordination; fresh workers with ECC as the sole TDD provider; intended RED/GREEN; unchanged model/effort/concurrency; real hook and browser execution; exact-thread restart/recovery. Review changed hook definitions natively. Demonstrate restoration of previous owned files/plugin identities before promotion.
4. Run affected build/type/test/coverage/security and separate Standards/Spec review. Missing required native evidence prevents readiness even when local tests pass. Keep final merge authorization separate.

The retained apps are reusable upgrade fixtures. A small plugin-only change can use focused installer/native recovery and application regression checks. Changed tool versions, routing, model, prompts, indexing or accounting warrant a newly versioned full comparison when token claims matter. Preserve v1 tags, contracts and results; never rewrite an old method to make a new candidate pass. Record new pins, runtime/transport fingerprints, order and allocation before outcomes.

## Contamination, recovery and measurement

For a new comparison, use fresh homes, sessions, branches and owned dependency/result caches from immutable starters. Never show active implementers the previous solution, added tests, review findings, graphs, recall or transcripts. Prior public solutions remain discoverable; rotate to a new but comparably scoped task/version when prior exposure is known or plausible. Do not automatically repeat or tune a completed pilot to chase a threshold. Two combined B runs cannot identify the causal contribution of each tool; that needs a separately selected factorial/ablation design.

After compaction/restart, discover the same concise execution record and phase guidance, reconcile Git/PR/source evidence, and recheck actual tool availability and graph freshness. RTK's executable/store and Graphify's on-disk graph persist independently of model context; remembered instructions do not prove use, correct binding or freshness. Rebuild stale graphs and count retrieval, indexing, compaction and recovery work. The separate [short recovery proof](../protocol/recovery-v1.md) demonstrates two installed manual checkpoints and exact-thread restart with real tool calls. It does not establish arbitrary repeated compactions, automatic near-limit quality, or preservation of every forgotten decision. No measured implementation naturally compacted; observed input peaks exceeded 100k and are reported explicitly.

The declared usage window includes upgrade, fixtures, tool provisioning/preflight, recovery probe, all four complete implementations, assessment and report preparation. Later administrative publication is excluded at the documented evidence freeze. Cached input and reasoning output are subsets, not additional totals. Recorded workflow tokens are not a bill; hidden upstream/background/retry work can remain unobservable. Keep unsuccessful outcomes, source digests and sanitized arithmetic public, and credentials/raw private transcripts private.
